Executive summary

Four raw feeds now flow into one ML-ready feature store and one label store, with every feature restricted to what the bank knew on application day

The pipeline is reproducible from a single command, partitioned by month so it can run as a scheduled job, and validated with a simple model that trains and generalises out of time.

The problem

The bank lends cash loans and wants to predict, at the moment of application, whether a customer will default (defined as 30+ days past due six months into the loan). This assignment prepares the data; Assignment 2 trains the model.

What was built

  • Bronze: raw monthly snapshots of the loan ledger, clickstream, customer attributes and financials, landed untouched and partitioned by snapshot_date.
  • Silver: typed and cleaned tables. Corrupted values (placeholders, stray underscores, impossible ages and account counts) become typed columns or explicit nulls.
  • Gold: a feature store (one row per customer per application month, 110 numeric features) and the Lab 2 label store (one row per loan, label observed at month 6).

Design decisions that matter

  • Point-in-time correctness: clickstream is aggregated over a 6-month window that ends at the application month; the 61% of clickstream rows dated after the application are never read.
  • No silent fixes: implausible values become null, never a clipped or guessed number.
  • Gold is numeric but un-imputed: scaling and imputation are model decisions fitted on the training split only, which prevents train-test contamination.
  • One function per table per layer, same pattern as Lab 2, orchestrated by main.py as a monthly backfill.

Bronze   Raw ingestion

Bronze keeps a faithful, replayable copy of every source snapshot, using the same ingestion pattern as Lab 2 for all four feeds

Nothing is interpreted at this stage. If a cleaning rule turns out to be wrong later, silver and gold are rebuilt from bronze without touching the source systems again.

Design choices

  • One partition per snapshot_date. A monthly job reads the source, keeps the rows of that snapshot and writes bronze_<table>_YYYY_MM_DD.csv. Backfilling history and running the next month are the same code path. A month without source rows writes no file, and silver and gold skip it.
  • Raw fidelity over convenience. Values such as 52312.68_ or __10000__ are landed exactly as received; csv keeps them human-readable for investigation.
  • One function, four sources. The Lab 2 function now also takes the table name and csv path; main.py calls it once per source, so adding a feed is one more entry in bronze_sources.
  • Source-system boundary. In production the csv read is the only line that changes: it becomes the database or API connector.

Why csv here and parquet later

Bronze is optimised for inspection and replay: analysts open a partition in any tool and see the source byte for byte. Silver and gold are optimised for Spark reads and typed schemas, so they switch to parquet. The layout mirrors Lab 2, which makes the label store and the feature store look identical to their consumers.

Silver   Schema and data quality

Silver enforces the schema and applies explicit, documented rules so that a corrupted value becomes a null, never a plausible-looking guess

Every rule was derived from the EDA and is written as a whitelist or a plausible range in code, so a reviewer can see exactly what was changed and why.

Why null and not a fix

Clipping 1,756 accounts to 30 or filling an unknown age with the average would present an invented number as fact. Null is honest, is handled natively by gradient boosting models, and lets the model pipeline impute with statistics learned from the training split only.

Gold   Feature store design

The gold feature store holds one row per customer per application month with 110 numeric features in six groups, ready to join to the label store

Feature engineering happens only here, from silver inputs, so every feature can be traced back to a cleaned column and a rule.

Grain and keys

Customer_ID + snapshot_date (application month). 12,500 rows, no duplicate keys, one parquet partition per month: gold_feature_store_YYYY_MM_DD.parquet.

Join contract with the label store

feature.Customer_ID = label.Customer_ID and feature.snapshot_date = add_months(label.snapshot_date, -6). The 6 months match the label definition 30dpd_6mob.

Features per group (110 in total)

Design principles

  • Numeric only. Categories are one-hot, ordinal or counted in gold, so any classifier can consume the table directly.
  • Nulls are preserved, nothing is scaled or imputed. Those steps depend on the training population and belong inside the model pipeline (fit on train, apply to test).
  • Point-in-time by construction. Attributes and financials are read from the application month's partition; clickstream is filtered to the six months ending there.
  • No PII, no label information. Name and SSN stop at silver; nothing from the loan ledger enters the feature store.
  • The window is a parameter. The 6-month look-back is an argument of the gold job, so a longer history is a config change.

Leakage controls

Features only see what the bank knew on application day: the window closes at month D, the label is read at month D+6, and nothing in between is used

The three classic leakage paths were each closed by a structural decision in the pipeline rather than by a manual check.

Temporal leakage

Risk: 61% of clickstream rows are dated after the application, and a naive join on the label's snapshot_date would use activity from month D+6.
Control: the gold job keeps only clickstream rows with 0 ≤ months before D < 6, so nothing dated after D is aggregated. Verified per customer: an applicant of June 2024 has 18 months of history, the window uses the last 6, and the 6 later months are untouched.

Target leakage

Risk: repayment fields (overdue amount, days past due, balance) describe the outcome itself.
Control: the loan ledger feeds only the label pipeline. No column from lms_loan_daily exists in the feature store, and the label store carries just the key, the label and its definition.

Train-test contamination

Risk: scaling, imputing or encoding with statistics of the full dataset leaks the test set into training.
Control: gold stores raw numeric values with nulls; no global statistic is computed in the pipeline. The sanity model splits by application month (train 2023, test Jan 2024 to Jan 2025) and fits its imputer and scaler on train only.

How to run & next steps

Two commands reproduce the whole datamart; the same modules are ready to be scheduled month by month and consumed by the model pipeline

Everything runs inside the provided container, so reviewers need Docker and nothing else.

Run it

# 1. build and start the environment (JupyterLab on http://localhost:8888)
docker-compose build
docker-compose up

# 2. in a JupyterLab terminal: build bronze, silver and gold (about 80 seconds)
python main.py

# 3. optional: join feature and label store, fit the sanity model
python sanity_check_model.py

Next steps

Assignment 2: model training pipeline.

Read both gold tables, apply the join contract, split by application month, fit imputation and scaling on train only, handle applicants without clickstream (from Jul 2024), and register the model with its feature list and label definition.

Schedule the monthly jobs.

Each layer function already takes a single snapshot_date; wrapping them as tasks in an orchestrator (for example Airflow) turns the backfill loop into a scheduled DAG with one run per month.

Data quality monitoring.

Log row counts, null shares and the share of rows hit by each silver rule per partition, and alert when a month drifts (for example a jump in placeholder values or in the clickstream averages).

Widen the feature store when the feeds allow.

Attributes and financials are captured once per customer today; if the source systems refresh them monthly, the same gold job can serve every customer every month, enabling re-scoring beyond the application moment.
